# 產品轉向提案：3 角色 ATB 格子戰場

## 目的

此文件用來確認 `newProject` 的核心玩法轉向。

現有版本雖然已完成地城、ATB、掉寶、玩家裝備、怪物與樓層框架的驗證，但在實際遊玩感上，單人爬塔 + 清場 + 換裝的循環存在明顯問題：

- 戰鬥決策密度不足，容易變成作業
- 怪物互動感偏弱，表現像殭屍貼近玩家
- 大地圖與樓梯流程增加了非決策移動成本
- 換裝雖然是主要樂趣，但戰鬥本身未能支撐長時間遊玩

因此，此案不再沿著原本的單人刷裝爬塔方向細修，而是轉向一個更聚焦的產品核心：

**3 角色小隊、ATB 時序、格子戰場、延遲結算、以位移 / 保護 / 控場為主的戰術對局遊戲。**

---

## 新核心定位

### 一句話版本

玩家操作 3 名角色，在小型競技場式格子戰場中，透過 ATB 輪動、位移、保護、換位、延遲傷害與功能型武器技能，擊殺敵方隊伍。

### 核心樂趣

本作的樂趣不再是單純堆高 DPS，而是：

- 看時間軸，判斷誰會先動
- 看危險區，判斷誰會先吃到技能
- 用位移或保護把隊友救出必吃傷害的位置
- 把敵人推進危險區或不利位置
- 透過武器與工具技能創造局勢優勢
- 在少量單位的盤面中做高密度決策

### 戰鬥主語

新方向下，戰鬥的主語是：

- 位置
- 時間
- 保護
- 延遲結算
- 局勢優勢

而不是：

- 純傷害最大化
- 清圖速度最大化
- 純數值成長驅動

---

## 小隊設計

### 隊伍編制

玩家在戰鬥中固定操作 3 名角色。

3 名角色的設計目的：

- 保留小隊分工與配隊樂趣
- 避免 4 角色以上造成 UI、操作與平衡爆炸
- 讓玩家能在有限認知負擔下追蹤整個戰場局勢

### 角色分工方向

每名角色應具有鮮明的盤面職責，而非只是數值差異。

例如：

- 前線承壓 / 卡位角色
- 功能位移 / 保護角色
- 輸出 / 收頭 / 控場角色

角色價值應建立在：

- 是否能保護隊友
- 是否能改變戰場位置
- 是否能放大危險區價值
- 是否能針對特定敵方類型做反制

而不是只建立在基礎攻防高低。

---

## 每名角色的行動配置

### 固定基礎行動

每名角色至少具備：

- 1 個基本移動

### 戰鬥技能槽位

每名角色配置：

- 3 個主武器
- 2 個工具 / 輔助技能

可視為：

- **3 個主動戰鬥技能**
- **2 個功能型輔助技能**

### 設計原則

主武器與工具的區別不應只是傷害高低，而是功能定位不同。

#### 主武器

主要承擔：

- 傷害
- 打點形狀差異
- 位移附加效果
- 延遲區域壓制
- 特定戰術用途

#### 工具 / 輔助技能

主要承擔：

- 保護
- 換位
- 推 / 拉 / 擋位
- 解圍
- 上狀態
- 觸發戰術連動

### 目標

玩家在自己的回合中，不是只思考「哪招傷害最高」，而是思考：

- 哪一招能救隊友
- 哪一招能把敵人送進危險區
- 哪一招能搶到下一輪先手
- 哪一招能迫使敵人放棄高價值位置

---

## 共通消耗品與戰鬥背包

### 隊伍共享背包

隊伍使用一個共通的戰鬥背包，所有角色共享消耗品資源池。

### 目的

這樣的好處：

- 降低每名角色各自管理物品的負擔
- 讓補給與資源分配成為隊伍層級的決策
- 使角色差異集中在戰鬥功能，而不是背包細節管理

### 消耗品定位

消耗品傾向設計為：

- 聚氣類
- 單次爆發類
- 緊急保命類
- 戰術扭轉類

而不是大量自體循環或常駐型的被動流程。

### 角色與道具的互動

可以保留少量角色特性，例如：

- 某角色使用道具效果更強
- 某角色使用消耗品不會影響主要節奏
- 某角色更擅長轉化背包資源為局勢優勢

這樣能產生「由誰下令使用道具」的額外決策，而不是所有角色用起來都一樣。

## 戰場設計方向

### 戰場不是探索地圖，而是競技場

新版本的地圖不再以探索與跑圖為主，而是以雙方遭遇的戰鬥場為主。

重點不在：

- 用地形強迫玩家繞遠路
- 用樓梯或出口延長流程

重點在：

- 讓戰場空間成為技能與位置博弈的舞台
- 讓雙方隊伍相遇後立刻進入對局

### 地圖形狀

**格子類型：六角格（pointy-top hexagonal grid）**

六角格取代方形格的理由：
- 6 個等距方向，無對角線模糊地帶
- 「前方 3 格 / 後方 3 格」自然定義背刺與保護語意
- 更自然的包圍圈形成，3 人小隊可做真正的三角卡位

基準戰場尺寸：**9 列 × 7 行**（63 格），大型遭遇可擴至 11×9。

尺寸應偏小至中型，確保：

- 單位間快速交戰
- 玩家容易讀懂盤面
- 位移、保護與範圍技能的價值高

#### 六角格方向定義

每個單位有一個「面朝方向」（六個方向之一）：

- **前方三格**：面朝方向 ±1 個方向（共 3 格），保護位的防護範圍、背刺的反面
- **後方三格**：面朝方向相反側的 3 格，觸發背刺加成（+20% 傷害）
- **側方**：剩餘 2 格，無背刺加成，但也不受保護

### 戰場特色格

可以明確加入標準化場地元素，例如：

- 魔法攻擊增幅格
- 物理攻擊增幅格
- 防禦 / 掩護格（受攻擊 -15%）
- 加速格（ATB 速度提升）
- 高風險高報酬格

但這些格子不應只是永久佔領就穩賺。

因為戰場上隨時有危險區與延遲傷害存在，玩家必須在以下兩者之間取捨：

- 站在高價值位置
- 避開即將到來的技能

這種取捨就是盤面張力來源。

## 戰鬥系統支柱

### 1. ATB 時間軸

ATB 不是輔助機制，而是核心資訊。

玩家必須持續思考：

- 哪個單位先動
- 哪個技能何時落地
- 哪位隊友在硬直中無法自救
- 我能否在技能落地前改變位置或保護目標

### 1.5 低頻高價值互動

新版本不追求高頻率的小傷害交換，而追求低頻但高權重的行動。

設計目標：

- 降低單位間的互相出手頻率
- 提高每次行動的局勢影響力
- 讓玩家在等待過程中持續判讀時間軸與盤面，而不是空轉

理想狀態下，每次出手都應至少影響下列其中一項：

- 傷害
- 位置
- 保護
- 讀條完成權
- 危險區控制權

### 2. 延遲結算

大量武器與技能應帶有：

- 前搖
- 延遲命中
- 預告範圍
- 區域危險標記

延遲結算的價值在於：

- 提供可讀性
- 創造預判空間
- 降低怪物 AI 需求
- 讓位移與保護變得有戰術意義

### 2.5 蓄力、打斷與保招

蓄力不只是節奏延遲，而應成為戰鬥核心對抗的一部分。

理想互動：

- 強力招式需要蓄力
- 蓄力過程可被打斷、位移破壞或角度破解
- 保護型角色可透過擋線、換位、掩體或控場保住隊友的大招
- 打斷型角色可專門破壞敵方高價值蓄力

如此一來，戰鬥的焦點會從純輸出最大化，轉變為：

- 保住己方關鍵行動
- 中斷敵方關鍵行動
- 爭奪行動完成權

### 3. 位移與保護

位移不是附屬效果，而是主系統之一。

例如：

- 推開敵人
- 拉回隊友
- 交換位置
- 瞬移保護
- 擋位
- 逼退
- 衝鋒切入

保護也不應只是單純加盾，而可以包含：

- 替隊友吃招
- 中斷敵方攻勢
- 把敵人從高價值位置推走
- 把硬直中的隊友救出危險區
- 擋在線路上阻隔射擊與投射物

### 3.5 區域效果與暫時戰場物件

除角色技能外，戰場本身也應能被短時間改造。

可行類型：

- 持續回復區
- 暫時性阻擋物
- 暫時性危險區
- 射線阻擋物
- 強化特定攻擊類型的區域

這些要素的目的，不是增加地圖複雜度，而是增加局勢爭奪點。

特別是暫時性阻擋物，可作為低成本但高戰術價值的設計：

- 幫蓄力角色遮擋敵方射線
- 切斷遠程火力線
- 迫使敵方改變站位或行動順序

### 4. 走法限制與攻擊形狀

本作可以借用象棋式設計思路：

- 角色或武器有不同走法 / 施放幾何
- 可傷害範圍大，但行動方式有限制

這樣的好處：

- 提升角色辨識度
- 讓盤面變成幾何問題，而不只是距離問題
- 讓武器特色更容易成立

### 4.5 方向與背後優勢

單位可保留朝向資訊，作為較進階但高價值的幾何規則。

方向系統建議先服務少數核心規則：

- 背後攻擊有額外收益
- 某些防護 / 擋線技能只保正面
- 某些技能使用前方錐形或扇形判定
- 某些打斷或刺殺動作要求側面或背面切入

方向系統應控制在「增加深度」而非「全面增加負擔」的程度。

## 怪物與 AI 方向

### 原則

怪物不追求高級 AI，而追求合理反應與盤面職責。

### 可行方向

怪物只需做到：

- 理解眼前哪些格子即將吃到玩家傷害
- 盡量避開明確的高風險格
- 優先攻擊硬直中或無法脫離危險區的角色
- 優先把玩家推向不利位置
- 針對戰場增益格做簡單爭奪

### 敵方職能

怪物設計應偏向戰術職能，而非單純追近輸出。

例如：

- 推位怪
- 放危險區怪
- 卡位怪
- 追擊收頭怪
- 保護型怪
- 擾亂時間軸的怪

如此一來，玩家才能真正去 build：

- 專門保後排的角色
- 專殺控制怪的角色
- 專門把敵方核心推離安全區的角色

---

## 地城框架保留，但改成服務戰鬥

### 整體結構仍保留地城

雖然產品核心轉向戰場對局，但地城外框仍可保留，作為：

- 戰鬥編排節奏
- 補給與換裝節點
- 敵方配置難度遞進
- Boss 戰壓軸

### 補給層

補給層改為純 UI 管理節點，而非實際地圖探索。

補給層功能可包含：

- 更換工具技能
- 更換消耗品配置
- 調整 3 名角色的狀態
- 補充背包中的聚氣類消耗品
- 檢視即將進入下一戰的敵方傾向

### 目標

補給層的存在是為了：

- 壓縮非戰鬥流程成本
- 讓 build / 準備集中化
- 保留節奏切換，而不拖慢遊玩

---

## 地城 loop 提案

### 基本 loop

可採用：

- 2 戰鬥
- 1 補給
- 重複 2 輪
- 最後 Boss

也就是基礎 7 層結構：

1. 戰鬥
2. 戰鬥
3. 補給
4. 戰鬥
5. 戰鬥
6. 補給
7. Boss

### 這個 loop 的優點

- 節奏清楚
- 不會拖太長
- 玩家能預期資源何時回補
- 補給節點能自然承接換裝與道具調整
- Boss 前有足夠準備空間

### 可變化部分

此為核心概念，不必所有地城都固定 7 層。

可依難度調整：

- 新手地城更短
- 高難地城增加一輪戰鬥 / 補給循環
- 特殊地城改成 1 戰鬥 1 補給 1 戰鬥 1 Boss 等節奏

---

## 舊方向中應弱化或暫停的部分

### 暫停作為核心的項目

以下項目不再作為當前版本的核心驅動：

- 大地圖探索與跑圖
- 清場後走樓梯的流程感
- 單人刷裝式循環
- 純 DPS 為主的武器價值
- 怪物主要靠追擊貼臉構成壓力
- 大量低差異掉寶來支撐內容量

### 弱化原因

這些設計會讓戰鬥重心偏離：

- 位置
- 時間
- 保護
- 局勢操控

而回到較難持久支撐的作業型循環。

---

## 現有引擎的殘留價值與重構邊界

此專案目前已有一套可運作的地城 + ATB + reducer 架構。雖然產品方向轉向，但現有引擎並非全部作廢。

### 可直接沿用或高度沿用的部分

#### 1. `state / action / reduce / event` 的權威架構

目前專案已具備以下核心分層：

- `state.ts`：純資料狀態
- `actions.ts`：行為入口
- `reduce.ts`：權威狀態修改
- `events.ts`：供 UI 播放的結果事件

這種架構本身非常適合新方向，因為：

- 多角色 ATB 戰鬥需要高可預測性
- 危險區 / 蓄力 / 打斷 / 位移都適合在 reducer 中權威結算
- UI 可以只負責顯示，不直接改狀態

#### 2. `atb.ts` 的時間推進概念

現有 `advanceTime()`、`pendingUnitId`、`castRemaining`、`recoveryRemaining` 很有價值。

這些概念可以直接支撐：

- 低頻高價值互動
- 蓄力招式
- 打斷與保招
- 單位硬直中無法自救的局面

也就是說，ATB 時序核心不是廢案，而是新方向的重要基礎。

#### 3. `state.ts` 內已有的 facing / hitMode / hazard 結構

目前狀態型別已經預留多個和新方向高度相容的欄位：

- `Unit.facing`
- `HitMode.delayed`
- `HitMode.persistent_zone`
- `Projectile`
- `HazardObject`
- `Cell.blockLineOfSight`

這代表：

- 方向 / 背刺不是從零開始
- 延遲傷害與危險區不是從零開始
- 暫時性阻擋物、射線阻擋、區域物件都有可延伸的型別基礎

#### 4. `guards.ts` 的幾何工具

目前 guards 內已有：

- `manhattan`
- `chebyshev`
- `pathLength`
- `hasLineOfSight`

這些幾何判定工具在新產品方向仍然非常有用，可沿用於：

- 走位限制
- 射線阻擋
- 正面 / 背後相關檢查的輔助
- 場上暫時性阻擋物判定

#### 5. 事件驅動 UI 的方向正確

`events.ts` 已有：

- `CAST_STARTED`
- `DAMAGE_DEALT`
- `PROJECTILE_FIRED`
- `HAZARD_PLACED`
- `ATB_READY`

這些事件型別很適合延伸成：

- `CAST_INTERRUPTED`
- `BLOCKER_PLACED`
- `GUARD_INTERCEPTED`
- `BACKSTAB_TRIGGERED`
- `ZONE_HEALED`

也就是說，事件模型可以沿用，只要增補。

### 可保留概念、但實作需要重寫的部分

#### 1. 現有 `guards.ts` 的行動驗證規則

目前 `canMove`、`canUseWeapon`、`canUseSkill` 還是建立在舊玩法假設上：

- 單位移動距離
- 傳統攻擊範圍
- 遠程 LOS
- 舊武器 actionId 表

這些邏輯的骨架能留，但具體規則應重寫，以符合：

- 3 人小隊
- 3 主武器 + 2 工具
- 位移 / 擋線 / 保護 / 方向
- 格子競技場對局

#### 2. `reduce.ts` 的具體戰鬥 case

目前 reducer 仍服務舊版地城戰鬥：

- 拾取掉落
- 清圖
- 樓層事件
- 舊武器 / 技能結算

新方向下，`reduce.ts` 的外殼與原則可以保留，但大多數具體 case 都需要重構。

#### 3. 目前的武器 / 傷害公式導向

現有 `damage.ts`、`weapons.ts`、`FormulaKeySet` 對於數值成長與詞條計算仍有參考價值，
但若新產品主體改為局勢、位移、保護與打斷，則其優先級會下降。

也就是說：

- 數值計算模組不是沒用
- 但它不應再主導設計
- 之後應變成支援「動作特色」的子系統，而不是核心支柱

### 建議直接弱化或停止沿用的部分

以下內容屬於舊產品方向遺產，若新方向確認，應降低優先級：

- 大地圖探索驅動的房間 / 樓梯流程
- 即時掉寶拾取流程
- 地城中走位服務探索，而非服務對局
- 以大量裝備與 affix 累積撐起主循環
- 怪物以 chase / patrol / guard 為主的舊 AI 目標

### 結論

現有引擎最有價值的殘留資產是：

- ATB 時序
- reducer / event 權威架構
- facing / hazard / delayed hit 的型別基礎
- 幾何與 LOS 判定工具

最不值得硬保的是：

- 舊地城流程
- 舊武器 action 表假設
- 舊版掉寶驅動戰鬥節奏

因此，最合理的做法不是整包丟掉，也不是原封不動延續，而是：

**保留引擎骨架，重做戰鬥語言。**

## 武器設計新要求

### 目標

武器不再只是殺傷動作，而是戰術工具。

### 武器應提供的價值類型

例如：

- 傷害 + 推位
- 傷害 + 拉位
- 傷害 + 延遲區域壓制
- 傷害 + 交換位置
- 傷害 + 保護隊友
- 傷害 + 封走位
- 傷害 + 中斷 / 延後敵方節奏

### 設計要求

每把主武器至少應有一個明確戰術用途，而不只是：

- 單體高傷
- 範圍中傷
- 低傷快招

否則玩家仍然只會回到「哪招數字最大」的決策。

### V1 武器技能結構範例

V1 可先把一個武器技能拆成：

- 動作骨架
- 時序孔
- 戰術孔
- 附魔孔

其中：

- 動作骨架負責定義武器 identity，例如突刺、橫掃、直線射擊、拉扯、保護衝撞
- 時序孔負責有限度地改變 cast / recovery / 打斷等級 / 保護等級
- 戰術孔負責推位、拉位、換位、擋線、危險區、護衛、打斷蓄力等核心 build 效果
- 附魔孔不只改屬性，還改變傷害表現方式，例如高傷火、燒傷火、打斷雷、限位冰

這樣可以保留武器基底特色，又讓 build 主要綁在可替換的插件上，而不是綁死在武器本體。

### V1 三孔模型

MVP 先做 3 孔即可：

- 時序孔
- 戰術孔
- 附魔孔

這 3 孔分別回答：

- 這把武器現在是快招、重蓄力、破招還是偏保守節奏
- 這把武器現在是推人、拉人、保人、設區還是打斷用途
- 這把武器現在採用什麼傷害語言與異常語言

純數值提升可先作為這三孔的附帶效果，不必獨立拆成第四孔，避免系統過早膨脹成單純堆倍率。

### 範例

以「鎖鏈突刺」為例：

- 動作骨架：直線 2 格命中單體，中等 cast，中等 recovery，原生可把自己拉近 1 格
- 時序孔：`壓縮節奏`，降低 cast，但略降傷害與打斷
- 戰術孔：`牽制鏈節`，命中蓄力中目標時追加打斷，並把目標拉近 1 格
- 附魔孔：`灼燒火`，直接傷害提升較低，但附帶燒傷 DoT

這種結構可以讓玩家清楚理解：

- 武器本身是什麼
- 目前 build 主題是什麼
- 為什麼它在隊伍裡負責這個角色

### 與成長循環的關係

此方向也與村莊工坊成長邏輯一致：

- 地城主要提供材料、貨幣與高級工坊產出資格
- 村莊內再用有限定方向的插件 / 卷軸 / 工坊流程，把武器技能塑造成需要的 build
- 高品質武器可提高基礎動作強度或承載能力，但不必保證擁有最適合的孔位配置

這可以避免「每撿一把新武器就全部重做」的作業感，並保留 build 可搬移、可調整的空間。

---

## 濃縮版未來展望

V1 先用 3 孔模型證明核心成立即可，未來若戰鬥語言穩定，再擴充：

- 傳奇插件：少量稀有插件可直接改寫特定武器動作，讓武器產生明確玩法變種
- 額外孔位：只給少數高級武器或特殊工坊產出，作為 build 承載力差異，而非單純數值上位
- 聯動效果：等基本節奏、位移、保護、附魔語言穩定後，再補更複雜的條件觸發與插件聯動

未來擴充的原則仍應維持：

- 武器基底保留 identity
- build 主要綁在可替換插件上
- 數值不是唯一追求
- 稀有內容應帶來玩法差異，而不只是更高數字

## MVP 優先順序

### 第一階段：先證明戰鬥核心成立

優先做：

- 3 角色小隊框架
- 小型戰場
- 初始站位配置
- 基本移動
- ATB 輪動
- 延遲危險區預告
- 3 主武器 + 2 工具的槽位框架
- 基礎位移 / 保護 / 換位效果
- 4 至 6 種怪物職能原型
- 戰鬥勝利 / 失敗流程

### 第二階段：補上地城 loop

- 補給層 UI
- 隊伍共通消耗品背包
- 消耗品補充與配置
- 7 層基礎 loop
- Boss 戰模板

### 第三階段：補成長與內容

- 角色 build 差異擴張
- 武器功能變體
- 消耗品深化
- 地城主題化戰場
- 更完整的敵方陣容與關卡組合

## 成功判準

此轉向是否成功，不應先看掉寶量或可刷內容，而應先看：

- 單場戰鬥是否有高決策密度
- 玩家是否會主動關注時間軸與危險區
- 位移與保護是否比純輸出更常成為正確答案
- 3 名角色是否有鮮明分工
- 怪物是否能在低成本 AI 下仍表現出戰術壓力
- 玩家是否會因戰場局勢而改變武器 / 工具選擇

如果以上成立，再往後補內容量才有意義。

## 結論

`newProject` 應從原本的單人爬塔刷裝原型，轉向為：

**以 3 角色小隊、ATB、格子競技場、延遲結算、位移 / 保護 / 控場為核心的戰術戰鬥遊戲。**

地城框架、補給節點與 Boss 結構仍可保留，但它們的角色從「內容量主體」改成「服務戰鬥節奏與 build 調整」。

未來所有系統設計都應優先回答一個問題：

**它是否強化了位置、時間、保護與局勢操控這四件事？**
