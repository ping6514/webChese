# 幽冥棋：能力（Abilities）設計與應用

本文定位：作為 **Soul/Item 能力的資料規格 + 引擎落點說明 + 長期通用化改造計畫**。

- 目標讀者
  - 想新增/調整卡牌能力的人（資料作者）
  - 想在引擎實作新能力的人（engine 開發者）
  - 想把 UI 做得更資料驅動的人（UI 開發者）

## 0. 目前狀態（2026-03）

- **本季 MVP3 狀態**
  - 本季 MVP3 可視為已完成。
  - 本輪重點不是再擴一套全新的能力框架，而是把既有 `abilities[]` 資料驅動方向補齊到可支撐新卡池重設。
- **本季已完成的核心工作**
  - `death-oath` 第二版能力已重整並同步補齊必要 engine 支援。
  - `gold-merc` 第二版能力已完成資料重設，且正式主檔 `app/src/data/souls/gold-merc.json` 已切換到新版配置。
  - 新增並落地的能力模板：
    - `FIRST_ATTACK_IF_GOLD_LT_GAIN_GOLD`
    - `FIRST_ITEM_USE_IF_GOLD_LT_GAIN_GOLD`
    - `ITEM_VALUE_AURA`
  - 上述新模板已接入攻擊 / 用道具 / stat aura 流程，並有對應測試與 build 驗證。
- **對「重構卡牌系統」的現階段結論**
  - 方向仍然是正確的：持續以資料驅動、通用欄位、可解釋 breakdown 為主。
  - 但本季採取的是 **漸進式重構**，不是一次性把所有 `ability.type` 改寫成統一 interpreter。
  - 目前更務實的做法是：
    - 先擴充可重用模板
    - 讓新卡池優先改寫到通用能力
    - 再逐步收斂舊能力 type 與 schema

## 1. 設計目標

- **資料驅動**
  - 卡牌能力應盡量用 JSON 資料描述（`abilities[]`），避免散落的 `if (soulId === ...)`。
- **可重播 / 可測試 / 可推導**
  - 引擎採 reducer + events，能力應能在 deterministic 狀態下重播。
- **高復用性**
  - 長期方向：把所有能力拆成少數幾個可組合的 primitives（條件、目標、修飾器、觸發時點、用量限制）。
- **UI 可解釋性**
  - 能力造成的屬性/傷害變化應能提供 breakdown（來源拆解），避免玩家只看到「數字跳了」卻不知道原因。

## 2. 能力資料模型（現況 + 建議）

### 2.1 Soul card 結構（簡化）

- 位置：`app/src/data/souls/*.json`
- 典型欄位：
  - `id/clan/base/name/costGold/stats/abilities/text`

`abilities` 是能力主體：

- `abilities: Ability[]`
- 每個 `Ability` 至少有：
  - `type: string`

### 2.2 通用欄位（推薦使用）

不同 `type` 會使用不同欄位，但建議能力逐步收斂到以下共同語彙：

- `when`
  - 描述 **何時/在什麼條件下** 能力有效。
- `targetWhen`
  - 描述 **目標單位需要滿足的條件**，常用於傷害修飾（例如只對宮內/越境目標加傷）。
- `for`
  - 描述 **作用對象**（例如只對過河單位、只對同 clan、只對宮內攻擊者）。
- `perTurn`
  - 描述 **每回合使用次數上限**（透過 `turnFlags.abilityUsed` 實現）。
- `count/amount/bonus`
  - 具體數值。
- `manaCost`
  - 額外資源成本；目前主要用在射擊強化能力（如 `CHAIN` / `PIERCE`）。
- `requiresManaGte`
  - 啟動門檻；目前主要用於「只有魔力達標時才能發動本次強化效果」。
- `onlyIfAtkKey`
  - 只有當攻擊者本次攻擊型態符合時才生效（例如 `magic` / `phys`）。
- `key/minDef`
  - 常見於 `TARGET_DEF_MINUS`：指定要降低哪種防禦、最低不能低於多少。
- `clan`（常見於 `RESONANCE`）
  - 避免「預設用卡的 clan」造成閱讀/維護模糊，推薦顯式標註。

### 2.3 統一 `abilities[]` schema 草案（A1）

本節目的：提供一份 **可落地、可逐步遷移、同時可讓 Soul/Item 共用** 的 `abilities[]` schema 草案。

- Soul card：`abilities[]` 代表常駐/被動/光環/觸發等能力。
- Item card：`abilities[]` 代表「使用道具」時會依序結算的效果。
  - **A1 約定：item 的 ability 若未填 `hook`，預設視為 `ON_USE`。**
  - 同一張 item 可以有多個 ability（用來表達「多段效果」）。

#### 2.3.1 Ability（建議欄位）

- `type: string`
  - 效果/模板名稱（例如 `AURA_STAT_BONUS`、`DISABLE_UNIT_ACTIONS`）。
- `hook?: Hook`
  - 觸發點。
  - Item A1：缺省視為 `ON_USE`。
- `when?: WhenExpr`
  - Gate（啟用條件）。建議逐步把既有零散欄位（例如 `perTurn`、部分 `when.type`）往這裡收斂。
- `limit?: Limit`
  - 使用限制（例如每回合最多 N 次）。
- `target?: TargetSpec`
  - 目標選取/限制（對應到 action payload 的 `targetUnitId/targetPos/choice`）。
- `params?: object`
  - `type` 專屬參數；盡量把「數值/旗標」放入此處，避免每個 ability type 在頂層長出完全不同欄位。
- `meta?: object`
  - 額外資訊（例如 UI breakdown label、資料來源 tag）。

#### 2.3.2 Hook（觸發點）

- `ON_USE`
  - Item：使用道具時。
- `PASSIVE`
  - Soul：常駐被動。
- `AURA`
  - Soul：光環效果（通常搭配 `target` 指向受影響單位集合）。
- `ON_KILL` / `ON_DEATH`
  - Soul/Item：事件觸發（若 item 未來要支援「回合內持續效果」也可用）。
- `ON_BEFORE_SHOOT_VALIDATE` / `ON_AFTER_SHOT_PLAN_BUILT`
  - 射擊 pipeline 的掛載點（用於規則覆寫、多段傷害等）。

> 注意：本文件先把 Hook 當作「概念層」；引擎落地時可以用現有的 pipeline hooks 逐步映射。

#### 2.3.3 WhenExpr（條件）

建議 `when` 支援以下結構（可由現況逐步擴充，不要求一次到位）：

- 原子條件（例）
  - `{ "type": "AFTER_CROSS_RIVER" }`
  - `{ "type": "ATTACKER_IN_PALACE" }`
  - `{ "type": "RESONANCE_ACTIVE", "clan": "dark_moon" }`
- 組合條件
  - `{ "and": [WhenExpr, ...] }`
  - `{ "or": [WhenExpr, ...] }`
  - `{ "not": WhenExpr }`

#### 2.3.4 Limit（使用限制）

建議把「每回合/每局的可用次數」從各能力零散欄位收斂為：

- `{ "perTurn": number }`
- `{ "perGame": number }`
- `{ "perTurnCap": number }`

#### 2.3.5 TargetSpec（目標）

目標設計需同時滿足：

- 可表達「需要玩家選擇」的 item
- 可表達「受影響集合」的 aura

建議最小集合：

- 單位選擇
  - `{ "type": "ALLY_UNIT" }`
  - `{ "type": "ENEMY_UNIT" }`
  - `{ "type": "ALLY_ENCHANTED_UNIT" }`
  - `{ "type": "ENEMY_ENCHANTED_UNIT" }`
- 棋盤格/屍骸
  - `{ "type": "ALLY_CORPSE_AT_POS" }`
- Aura 受影響集合（由引擎解釋成「哪些單位被套用」）
  - `{ "type": "CLAN_UNITS", "clan": "dark_moon" }`
  - `{ "type": "CROSS_RIVER_ALLIES" }`
  - `{ "type": "ALLIES_IN_PALACE" }`

若一個能力需要同時表達「選擇目標」與「套用到某集合」，可在 `params` 內再細分（避免把所有狀況塞進一種 target）。

#### 2.3.6 A1 Examples（JSON）

Item：`骸骨煉化`（多段效果 + choice resource）

```json
{
  "id": "item_bone_refine",
  "timing": "buy",
  "abilities": [
    {
      "type": "REMOVE_CORPSE",
      "hook": { "type": "ON_USE" },
      "target": { "type": "ALLY_CORPSE_AT_POS" }
    },
    {
      "type": "CHOICE_GAIN_RESOURCE",
      "hook": { "type": "ON_USE" },
      "params": {
        "options": [
          { "resource": "gold", "amount": 9 },
          { "resource": "mana", "amount": 2 }
        ]
      }
    }
  ]
}
```

Item：`冥鎖封印`（選擇敵方單位 + until turn end 的狀態效果）

```json
{
  "id": "item_nether_seal",
  "timing": "combat",
  "abilities": [
    {
      "type": "DISABLE_UNIT_ACTIONS",
      "target": { "type": "ENEMY_UNIT" },
      "params": {
        "until": "TURN_END",
        "disable": { "move": true, "shoot": true }
      }
    }
  ]
}
```

Soul：`EXTRA_SHOT`（暗月；帶 when + limit）

```json
{
  "type": "EXTRA_SHOT",
  "hook": { "type": "PASSIVE" },
  "when": { "type": "AFTER_CROSS_RIVER" },
  "limit": { "perTurn": 1 }
}
```

Soul：`AURA_STAT_BONUS`（推薦形式；for/target 明確化）

```json
{
  "type": "AURA_STAT_BONUS",
  "hook": { "type": "AURA" },
  "target": { "type": "CLAN_UNITS", "clan": "dark_moon" },
  "params": {
    "bonus": { "atk": 1, "def": 1 }
  }
}
```

#### 2.3.7 Primitives Catalog（TODO 75，權威分類草案）

本段是把現有 souls + rulebook items 的能力資料歸納成可重用 primitives，目的不是一次「統一所有能力 type」，而是提供一套分類，讓你在新增/調整能力時可以先問：

- 這是 **什麼 hook**？（什麼時點進 pipeline）
- 這需要 **什麼 gate**？（when/limit）
- 這影響 **誰**？（target/for）
- 這做 **什麼效果**？（modifier / effect）

分類草案：

- **Timing / Hook**
  - `ON_USE`（item 使用）
  - `PASSIVE`（常駐）
  - `AURA`（光環）
  - `ON_KILL` / `ON_DEATH`
  - `ON_BEFORE_SHOOT_VALIDATE` / `ON_AFTER_SHOT_PLAN_BUILT`
- **Condition / Gate（when）**
  - 位置/地形：`AFTER_CROSS_RIVER`、`SOURCE_IN_PALACE`、`ATTACKER_IN_PALACE`、`ALLIES_IN_PALACE_GTE`
  - 回合旗標：`MOVED_THIS_TURN`、`ENEMY_KILLED_THIS_TURN_GTE`
  - 共鳴：`RESONANCE_ACTIVE`（對應 `RESONANCE { need, clan }`）
  - 資源/數量：`CORPSES_GTE`、`SOLDIERS_GTE`
- **Targeting**
  - 單位：`SELF` / `ALLY_UNIT` / `ENEMY_UNIT` / `ALLY_ENCHANTED_UNIT` / `ENEMY_ENCHANTED_UNIT`
  - 棋盤格：`UNIT_AT_POS`、`ALLY_CORPSE_AT_POS`
  - 集合（aura）：`CLAN_UNITS`、`CROSS_RIVER_ALLIES`、`ALLIES_IN_PALACE`
- **Effect / Modifier（效果本體）**
  - 規則覆寫：`IGNORE_BLOCKING`、`IGNORE_PATH_BLOCKING`、`MOVE_THEN_SHOOT`、`EXTRA_SHOT`
  - ShotPlan 擴展：`SPLASH`、`CHAIN`、`COUNTER`
  - 傷害修飾：`DAMAGE_BONUS`、`AURA_DAMAGE_BONUS`
  - 屬性修飾：`ATK_BONUS`、`AURA_DEF_BONUS`、`AURA_STAT_BONUS`
  - 行為/資源：`FREE_SHOOT`、`GAIN_NECRO_ACTION`、`INCOME_BONUS`、`CHOICE_GAIN_RESOURCE`
  - 狀態控制：`DISABLE_UNIT_ACTIONS`（until turn end）
  - 牌庫/展示：`REFRESH_ITEM_DISPLAY`、`REFRESH_SOUL_DISPLAY_ALL`

本節提供「資料欄位白名單」草案，目標是後續可以加一個 JSON lint 來避免：

- `when.type` / `for` 寫了但引擎不支援，造成玩家/資料作者誤解

`when.type`（目前引擎已處理/出現過的集合，後續新增需同步更新引擎與 lint）：

- `AFTER_CROSS_RIVER`
- `ATTACKER_IN_PALACE`
- `SOURCE_IN_PALACE`
- `RESONANCE_ACTIVE`
- `MOVED_THIS_TURN`
- `ENEMY_KILLED_THIS_TURN_GTE`
- `CORPSES_GTE`
- `SOLDIERS_GTE`
- `ALLIES_IN_PALACE_GTE`

`for` keys（目前引擎已處理/出現過的集合）：

- `MOVE`
- `CLAN`
- `CROSS_RIVER_UNITS`
- `ALLIES_IN_PALACE`

## 3. `when`：條件（Condition）

### 3.1 `when` 的核心定位

`when` 用來 gate（啟用/停用）能力；同一個能力 type 可在不同 `when` 下重用。

### 3.2 常見 `when.type`（以引擎現況為準）

- `AFTER_CROSS_RIVER`
  - 常用於「越境」能力。
- `ATTACKER_IN_PALACE`
  - 典型用於「宮內射擊」類能力。
- `RESONANCE_ACTIVE`
  - 需要同卡或同魂卡提供 `RESONANCE` 定義（need/clan）。
- `MOVED_THIS_TURN`
- `ENEMY_KILLED_THIS_TURN_GTE`
- `CORPSES_GTE`
- `SOLDIERS_GTE`

注意：目前 `when` 多為「單條件」；若未來需要複合條件，建議新增可組合的 `AND/OR/NOT`（見第 8 節改造計畫）。

### 3.3 `targetWhen`（目標條件）

`targetWhen` 用來描述「這個 modifier 不是看攻擊者狀態，而是看目標是否符合條件」。

目前已落地支援：

- `TARGET_IN_PALACE`
- `TARGET_CROSS_RIVER`

典型用途：

- `DAMAGE_BONUS`：只對宮內目標 / 越境目標加傷
- 後續也可擴充到其他 target-based modifier，但新增時要同步補 `damage.ts` 與 `shotPreview.ts`

---

## 4. `for`：目標（Target Filter）

### 4.1 `for` 的核心定位

`for` 用來限制能力影響到的對象集合。

### 4.2 常見 `for` key

- `MOVE`
  - 目前用於 `IGNORE_PATH_BLOCKING`：只在「移動合法格計算」生效。
- `CROSS_RIVER_UNITS`
  - aura/bonus 常用：只對過河友軍。
- `CLAN`
  - aura/bonus 常用：只對同 clan。

注意：目前有些能力還沒完全統一 `for` 的語意與支援範圍；新增能力時建議優先沿用現有 key，避免擴散。

## 5. 常見能力類別與引擎落點（實作地圖）

本章以「能力影響哪一段 pipeline」來分類，方便你思考能力應該寫成哪種通用模板。

### 5.1 行動合法性 / 規則覆寫（Move/Shoot Validation）

- 典型能力
  - `IGNORE_PATH_BLOCKING`（for MOVE）
  - `IGNORE_BLOCKING` / `AURA_IGNORE_BLOCKING`（射擊無視阻擋）
- 引擎落點
  - 移動：`app/src/engine/legalMoves.ts`
  - 射擊合法：`app/src/engine/shooting.ts` + `app/src/engine/effects.ts`（shootRules override）
  - 預覽：`app/src/engine/shotPreview.ts`
- 要點
  - **同時更新「合法性」與「預覽」**，避免 UI 顯示可射但引擎說不行（或反過來）。

### 5.2 ShotPlan 擴展（Multi-hit / Splash / Chain / Counter）

- 典型能力
  - `SPLASH`
  - `COUNTER`
- 引擎落點
  - `app/src/engine/effects.ts`（`onAfterShotPlanBuilt` 擴 plan）
  - `app/src/engine/shotPlan.ts`（按 instance 執行）
  - `app/src/engine/shotPreview.ts`（鏡像出預覽效果）
- 要點
  - 任何會「新增/改變 instance」的能力，都應在 preview 有等價呈現。

### 5.3 傷害修飾（Damage Modifiers）

- 典型能力
  - `DAMAGE_BONUS`
  - `AURA_DAMAGE_BONUS`
  - `SOLDIERS_TIERED_AURA_DAMAGE_BONUS`
  - `TARGET_DEF_MINUS`
- 引擎落點
  - 計算：`app/src/engine/damage.ts`
  - 預覽：`app/src/engine/shotPreview.ts`
- 要點
  - 傷害型加成建議集中在「射擊預覽 breakdown」呈現（避免 unit 面板塞太多）。
  - `TARGET_DEF_MINUS` 目前已支援：
    - `key`
    - `amount`
    - `per: { type: 'CORPSES_PER', count }`
    - `amountPer`
    - `onlyIfAtkKey`
    - `minDef`

### 5.3.1 `MINGLEI` 的淘汰與通用替代

`MINGLEI` 原本是 Styx 的風味型能力名，但其效果本質其實是兩個可通用 primitive 的組合：

- `TARGET_DEF_MINUS`
- `DAMAGE_BONUS` + `targetWhen`

目前建議：

- **不要再新增 `MINGLEI` 類型**
- 舊效果請改寫為通用能力組合

Styx「冥雷」推薦寫法：

```json
[
  {
    "type": "TARGET_DEF_MINUS",
    "key": "magic",
    "amount": 2,
    "onlyIfAtkKey": "magic",
    "minDef": 0
  },
  {
    "type": "DAMAGE_BONUS",
    "amount": 2,
    "targetWhen": { "type": "TARGET_CROSS_RIVER" }
  }
]
```

好處：

- 能明確表達「降哪種防」
- 能支援未來的 `phys` / `magic` 泛化
- 不再依賴 clan 專屬命名，資料更可重用

### 5.4 屬性修飾（Stats Modifiers）

- 典型能力
  - `ATK_BONUS`
  - `AURA_DEF_BONUS`（舊）
  - `AURA_STAT_BONUS`（新：可同時加 atk/def/hp）
- 引擎落點
  - 計算：`app/src/engine/stats.ts`
  - UI 面板：`RightPanelV2.vue` / `UnitInfoPanel.vue`
- 要點
  - 屬性型變更應可提供 breakdown（base + bonus parts）。
  - 長期建議：所有屬性 aura 都走 `AURA_STAT_BONUS`，避免同類型重複能力。

### 5.5 生命值特殊規則（HP / MaxHP / Heal）

- 典型能力
  - `AURA_STAT_BONUS` 的 `bonus.hp` 與可選 `bonus.healCurrent`
- 引擎落點
  - `stats.ts`：maxHP 計算與面板 breakdown
  - `reduce.ts`：在特定 action 後做一次性補血（保守：ENCHANT/REVIVE 後）
- 要點
  - MaxHP 改變與 current HP 的關係務必定義清楚（是否補滿、是否一次性）。

### 5.6 共鳴（Resonance）

- 典型能力
  - `RESONANCE { need, clan }`
  - 搭配 `when: { type: 'RESONANCE_ACTIVE' }`
- 引擎落點
  - `stats.ts` / `damage.ts` / `effects.ts`：以 `isResonanceActive` 類 helper gate
- 建議
  - `RESONANCE` 建議 **顯式填 `clan`**（可讀性/維護性更好）。

## 6. UI 顯示建議（可解釋性）

### 6.1 面板（UnitInfoPanel）顯示什麼？

- 面板建議顯示：
  - **ATK/DEF/HP 的總值 + breakdown（黃色 suffix）**
- 不建議在面板塞：
  - 傷害型加成的細節（`DAMAGE_BONUS/AURA_DAMAGE_BONUS`）
  - 這類應放在射擊預覽內

### 6.2 射擊預覽（ShotPreview）顯示什麼？

- 顯示
  - 阻擋規則覆寫（例如忽略 N 阻擋）

- **定義能力語意**

### 7.2 `onActivate` 子能力（目前規格與限制）

目前 `onActivate` 主要出現在 `BLOOD_SACRIFICE`，代表：

- 先支付一段啟動成本（通常是 king HP）
- 再把一個「本次行動的附加效果」掛到本次射擊上

引擎現況（authoritative source：`app/src/engine/reduce.ts`）：

- `BLOOD_SACRIFICE.onActivate`
  - 若 `type === 'MOVE_THEN_SHOOT'`
    - 走特例：寫入 `turnFlags.bloodSacrificeMoveThenShoot`
  - 否則
    - 寫入 `turnFlags.bloodSacrificeActiveShotEffect`
    - 由後續 shot pipeline 視為本次射擊的額外效果

### 7.2.1 目前建議視為「已支援」的 `onActivate.type`

- `DAMAGE_BONUS`
- `CHAIN`
- `PIERCE`
- `IGNORE_BLOCKING`
- `MOVE_THEN_SHOOT`

### 7.2.2 `onActivate` 子能力建議沿用的通用欄位

若該子能力本身在主能力已支援這些欄位，`onActivate` 內也**應以相同語意解讀**：

- `when`
- `targetWhen`
- `perTurn`
- `count`
- `amount`
- `radius`
- `mode`
- `manaCost`
- `requiresManaGte`
- `onlyIfAtkKey`
- `key`
- `minDef`

### 7.2.3 目前規格與實作的落差

雖然規格上建議 `onActivate` 應沿用主能力欄位，但目前引擎落地仍有幾個現況限制：

- `onActivate` 的正式入口目前只有 `BLOOD_SACRIFICE`
- `MOVE_THEN_SHOOT` 是 reducer 層特例，不是通用 shot effect handler
- 不是所有主能力欄位都已明確覆蓋到 nested `onActivate` 的 preview / validate / execute 三側一致性

因此目前建議：

- **資料作者可以優先沿用主能力同名欄位**
- **但若要新增新的 `onActivate.type` 或新欄位組合，需同步補測試**
- 後續 engine TODO：把 `onActivate` 視為「子能力能力樹」，改由通用 ability interpreter 處理，而不是 reducer 特例分流

## 13. 提案：傷害加成收斂（TODO 68）

現況：

- `DAMAGE_BONUS`（自帶/條件性）：在 `damage.ts` 與 `shotPreview.ts` 都有資料驅動 gate，但兩處細節容易分岔
- `AURA_DAMAGE_BONUS`（光環型）：在 `damage.ts` 與 `shotPreview.ts` 都有一段相似但非完全一致的計算邏輯（when/for/per）

目標：

- 讓「傷害型加成」像 `AURA_STAT_BONUS` 一樣，有一套可擴充且一致的 schema
- 讓 preview 與實際計算共享同一套 gate/解析，降低 bug

### 13.1 相容策略（先鋪路，後遷移資料）

先在引擎允許以下 alias type：

- `DAMAGE_MODIFIER`：語意等同 `DAMAGE_BONUS`（自帶/條件性傷害加成）
- `AURA_DAMAGE_MODIFIER`：語意等同 `AURA_DAMAGE_BONUS`（光環型傷害加成）

短期：資料仍可維持使用 `DAMAGE_BONUS/AURA_DAMAGE_BONUS`。

中期：逐 clan 遷移到 `*_MODIFIER` 後，可將舊 type 標記為 deprecated。

### 13.2 建議 schema（草案）

（本段是方向，不要求一次落地）

- `type: 'DAMAGE_MODIFIER' | 'AURA_DAMAGE_MODIFIER'`
- `when?: WhenExpr`
- `for?: ForKeys`（例如 `CLAN`、`CROSS_RIVER_UNITS`）
- `clan?: string`（for=CLAN 時必填）
- `params:`
  - `amount?: number`
  - `per?: { type: 'CORPSES_PER' | ...; count: number }`
  - `amountPer?: number`
  - `targetWhen?: ...`（例如 `TARGET_IN_PALACE`）

> 長期也可以評估把傷害 modifier 的 `for/when` 統一成與 `AURA_STAT_BONUS` 同一套 filter helper，讓所有 aura 都走同一條 gating code path。
